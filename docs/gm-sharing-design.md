# GM共有修正：設計レビュー（実装途中・未公開）

基準 main `055c040d06e67895ea9a7fa62dda72d95b978a62`（v1.48.5）。作業 branch `codex/gm-share-scope`。v1.48.6は未採番。実Drive/Sheets/権限への操作なし。

## 確認した問題

- `canSee`は会社リストにGM会社が含まれれば許可していた。単社の役割「社員」、GM兼務なし、同じ会社だけを許可するローカル修正を追加した。全社役割の既存範囲は維持。
- `readersMatch` / `sharesMatch`は社員一覧内メールだけを根拠に既存reader/writerを削除・変更する。誰が付与した共有かを証明していない。
- `adminRoleSave`は役割を保存してから共有処理を行う。現在は共有差分プレビューがない。
- `adminAdd`は本人writer付与を別経路で行い、`adminRemove`は共有IDがなければメールから探して削除する。役割保存だけ直してもこれらの経路が残る。
- `permList`はページ送りを実装していない。欠落した権限を「存在しない」と扱ってはならない。

## 解除保証の限界（設計判断点）

Driveのpermission.idは付与先の識別子であり、HUBの付与操作の世代を識別しない。同じfileId/permissionId/email/roleの共有が外部操作で削除・再付与された場合、現在の権限一覧だけでは区別できない。Googleは同一ファイルへの権限変更の並行実行をサポートせず、最後の変更が適用されると明記している。したがって読取り直後の外部変更まで含めた「絶対に無関係共有を消さない」と「役割解除時に必ず自動解除する」は、現在のAPIだけでは同時保証できない。

- https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions
- https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions/create
- https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions/delete

## 推奨する保守的な実装案（まだ未実装）

1. 社長の既存社員一覧に、別タブ「共有管理履歴」を追加。既存社員列・指示箱契約は変えない。履歴は追記のみで、管理元listId、operationId、fileId、対象社員/付与先Gmail、permissionId、before/after role/type/inherited、intent/response/verified/revoked/uncertain、UTC日時を保存する。読戻し確認できなければ次の権限操作を行わない。
2. 新規付与前に全ページの権限を取得。既存共有は「再利用・HUB解除対象外」として保持。旧共有を管理済みに自動移行しない。writer等の既存権限を勝手に降格・昇格しない。
3. 新規作成・役割変更・解除を同じ差分計画に集約。氏名、シート名/ID、付与先、現在権限→予定権限、再利用/要確認を一覧表示。確認前は役割保存・権限変更をしない。新規ファイルは新規作成予定と明記し、実ID確定後に再確認する。
4. 確認後も社員一覧・接続元listId・権限スナップショットを再読し、変更があれば計画破棄・再確認。旧一覧を使う別端末も履歴を取得してから計画する。履歴の欠落・破損・読取失敗では自動解除しない。
5. 新規付与の正常応答と読戻し確認を記録できたもののみ管理対象候補。POST成功後に通信/履歴保存が不明なら、再試行で既存共有を見つけてもHUB所有と推定せず要確認。重複POSTしない。
6. DELETEは管理履歴と現在の権限が一致するものだけを再提示して明示確認。外部変更・継承権限・履歴不明は残す。実行後の不在を読戻して完了扱いにする。途中取消・失敗は完了済みと未実行を分け、勝手な巻戻し操作はしない。
7. 管理処理は1端末・1タブずつ。通常同期と管理操作を同時実行しない。外部のDrive共有操作も同時にしないという運用条件が必要。ただし同じ値の外部再付与を現在の権限だけで検知できない限界は残る。絶対保証が必要なら、解除は管理者の別途精査に止めるか、追加の監査/排他基盤を設計する必要がある（今回未承認の権限拡大は行わない）。
