# v1.48.6 GM範囲と共有管理

基準：main `055c040d06e67895ea9a7fa62dda72d95b978a62`（v1.48.5）。branch `codex/gm-share-scope`。

## 範囲

GMの相手は同じ単一会社の一般社員だけ。複数会社・全社・GM・GM兼務者・本人・役割解除済みを除外する。全社＋GM会社の兼務は「全社」の範囲を維持する。社員シートreaderと指示箱writerの両方に同じ判定を使い、GMの旧読取キャッシュも表示時に範囲を絞る（保存キャッシュは削除しない）。旧共有が残ればGoogleでのアクセスは続く。アプリの表示制限とDriveのアクセス権を混同しない。

既存の案件・ToDo・予定・数字の計算、社員共有列、指示箱/報告契約、OAuth scopeは変えない。共有変更中の同一タブのまとめて同期だけは競合防止のため待機案内する。

## 実行フロー

1. 社長の管理アカウント・最新社員一覧・端末保存状態を確認。有効な社員だけGmailの一意性を検査し、削除済みの同Gmail履歴は残す。記録/指示箱/見る人用一覧のファイルIDは削除済みも含め別物であることを確認する。異常なら新規ファイル作成前に止める。同一タブの二重操作を止める。
2. 新しい社員シート・指示箱・見る人用一覧が必要なら、作成予定を先に確認する。この段階では権限を付けない。作成済みのファイルIDは保持し、途中中止でも削除しない。初期化失敗は自動で既存内容を上書き修復せず停止する。
3. 全ページの権限と共有管理履歴を読み、誰のどのファイル（ID）に、どのGmailの何の権限を付ける／外す／維持／残して要確認にするかを一覧表示。役割変更も表示。「やめる」・Escapeは共有も役割も変えない。新ファイル作成済みの場合はそのファイルだけ残る。
4. 「一覧を確認して実行」後、社員一覧・接続先・トークン・権限・履歴を再照合。変化があれば再計画せず停止する。
5. 各変更前にintentを追記・読戻し。直前の権限も再照合する。付与/解除の結果を読戻し、他の権限が変わっていないことを確認し、verifiedを追記・読戻しする。前段の確認が失敗したら後段は実行しない。
6. 「共有変更を中止（次の変更から）」は現在の結果確認を終え、次の変更を止める。完了済みの共有を勝手に巻き戻さない。途中結果は画面ログと履歴に残す。役割保存前の中止・失敗では役割は元のまま。新規社員の作成途中には一般社員の登録が残る場合がある。
7. 最後に役割を保存し、社員一覧を読戻す。端末保存を確認できなければ以降の書込みを止める。書込み結果が不明なら再読込して確認する。

既存共有は同じ権限なら再利用するが、当機能の所有と推定しない。役割違いの既存共有をPATCHで昇格・降格しない。旧共有・履歴不整合・外部変更・未完のintentは要確認として残す。役割を外したという表示は、全共有の解除成功を意味しない。個別の対象と理由を確認する。新規共有は通知メールを自動送信しない。

## 履歴の保存先・互換・機密情報

- 保存先：社長の既存 `CPG HUB_社員一覧` spreadsheet 内、新タブ **共有管理履歴**。
- A〜C：**操作ID / 段階 / 記録JSON**。ヘッダー初期化は固定A1:C1。データ行はappendのみ（全clear・更新・並べ替えなし）。同名タブは見出しを検証し、違えば停止。
- JSON：管理元listId、操作UUID、grant/revoke、対象fileId、付与先Gmail、権限ID・role、intent/verified、UTC ISO日時。grantは「なし→role」、revokeは「role→なし」の記録。表示名は社員一覧で照合する。
- 含まれる機密情報は社員のGmail・内部ファイルID・アクセス権と操作時刻。案件本文や金額・OAuthトークン・認証秘密は保存しない。履歴の閲覧権限は既存の社員一覧ファイルのACLに従う。新しい相手への共有や追加OAuth scopeは不要。
- **公開後に社長が管理操作の最終一覧を明示確認した時だけ作る**。初回起動・通常同期ではタブ作成や移行をしない。開発では実表へのタブ作成/移行は一度も実行しない。
- 既存社員列・指示箱列は不変。旧社員版はこのタブに触れない。旧管理版は安全機構なしで権限を変更できるので、全管理端末・旧タブを更新してから管理する。旧版の自動拒否や更新証明機構はない。
- 別端末・以前の一覧を再利用しても同じ管理表の履歴を読む。別listIdの履歴は受理しない。履歴が存在しない旧共有を自動移行しない。履歴を失った場合は共有を再利用しても解除対象にしない。
- 付与成功後の応答紛失・履歴保存失敗はintentのまま残り、次回も盲目的なPOST/DELETEをしない。正常完了分は再試行時に維持し、未実行の新規分だけ再確認できる。権限・見る人用一覧・社員一覧の更新は単一トランザクションではなく、途中失敗時は一部だけ反映される場合がある。画面ログと各読戻し結果を確認し、同じ役割変更を改めてプレビューする。結果不明分の解決は管理者の個別調査であり、このPRは実データの修復UIや自動修復を追加しない。

## 保証できない範囲

Driveのpermission.idは付与先の識別子であり、HUBの付与操作の世代IDではない。同じfileId/permissionId/email/roleで外部から解除・再付与された共有は、現在のAPIだけでは区別できない。Googleは同一ファイルへの権限変更の並行実行をサポートしない。管理操作は1端末・1タブで、Drive側の共有編集と同時実行しない運用が必要。チェック後から変更までの競合を原子的に排除するバックエンドロックはない。「必ず全部外れる」「無関係な同値再付与まで識別できる」とは保証しない。

- [Permission resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions)
- [permissions.create](https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions/create)
- [permissions.delete](https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions/delete)

現在すでに付いている広すぎる共有の実際の修正は別途本人確認が必要。このPRを公開するだけで旧共有が解除されることはない。
